Question 1 — Modèle de déploiement

C'est la décision architecturale la plus importante. Elle conditionne tout le reste : base de données utilisateurs, paiements, UX.

A

Application Desktop (Qt) — avec licence activée en ligne

ViPPer reste une app Python/Qt installée sur le poste du bureau d'études. Un serveur de licences gère les abonnements. L'utilisateur se connecte une fois pour activer, puis travaille hors-ligne.

  • ✅ Pas de refonte de l'interface
  • ✅ Données locales (sensibles pour les BEs)
  • ✅ Performances maximales (calcul local)
  • ⚠️ Distribution plus complexe (installeur, mises à jour)
  • ⚠️ Piratage possible si la protection de licence est faible
B

Application Web SaaS (navigateur)

ViPPer devient une webapp (ex: FastAPI + React/Vue). Le calcul tourne côté serveur. L'utilisateur accède via navigateur, sans installation.

  • ✅ Abonnements & paiements natifs (Stripe intégré simplement)
  • ✅ Mises à jour immédiates pour tous les utilisateurs
  • ✅ Accessible depuis n'importe quel poste
  • ⚠️ Réécriture complète de l'UI (gros chantier)
  • ⚠️ Données projet envoyées sur un serveur (confidentialité)
  • ⚠️ Coût d'hébergement (serveur de calcul)
C

Hybride — Desktop + Portail Web pour la gestion

L'app de calcul reste en desktop Qt (performances, données locales). Un portail web léger gère les comptes, abonnements et téléchargements. Les deux communiquent via une API.

  • ✅ Meilleur des deux mondes
  • ✅ Paiement & gestion via le web (simple avec Stripe)
  • ✅ Données de projet restent locales
  • ⚠️ Deux systèmes à maintenir
  • ⚠️ Complexité d'intégration (token d'activation, API)
